# 王者荣耀 · 阿轲 / 司马懿 皮肤监控（云端定时）

每天自动检查一次（定时任务设在北京时间 07:00 触发，GitHub 排队后实际约 07:10 ~ 08:00 之间），发现「新皮肤上线」或「皮肤返场公告」就推送提醒。  
跑在 GitHub Actions 云端，**和你电脑开不开机完全无关**，不需要自己的服务器。

## 提醒规则：两条线，各自独立

| 情况        | 起算 / 结束                                        | 提醒区间                                    |
| --------- | --------------------------------------------- | --------------------------------------- |
| 新皮肤       | 图鉴里的**上线日期**起 10 个自然日                         | 第 1 天 ~ 第 10 天，每天提醒一次                   |
| 限时返场      | 公告正文里的**官方返场起止日期**（如 11/1–11/5）               | 开始前 3 天内预告 + 返场期内**每天**提醒，到期自动停         |
| 返场但没写结束日  | 公告发布日期 / 发现日为起点                             | 退回 10 天窗口                               |
| 超出区间      | —                                             | 自动不再提醒，无需手动清理                           |

每条提醒都会标注进度：新皮肤显示「第 3 天，还会再提醒 2 天」，返场显示「还剩 4 天截止 / 今天是最后一天」。
两条线**互不覆盖**：同一天既有新皮肤上线、又有别的皮肤返场，会分成两条分别推送。

## 检测原理（两条独立信号）

| 信号     | 数据源                                                      | 判断方式                                             |
| ------ | -------------------------------------------------------- | ------------------------------------------------ |
| 新皮肤上线  | 皮肤图鉴接口 `https://pvp.qq.com/zlkdatasys/heroskinlist.json` | 该英雄在图鉴中新增一条皮肤记录 → 判定上线，并带出品质 / 获取方式 / 上线日期 / 详情页 |
| 限时返场   | 公告正文 `https://1.pvp.qq.com/gicp/news/651/{tid}.html`      | 解析正文里的结构化字段：返场皮肤、返场时间、返场价格 → 按官方真实起止日期提醒        |

> **公告正文去哪抓？** `newsdetail.shtml?tid=` 是 JS 空壳，真正正文由上面的 gicp 静态页渲染。
> 正文里返场是结构化的，实测样本：
>
> ```
> 返场皮肤：妲己-愿照·众生和、司空震-愿照·山河定、西施-续相思
> 返场时间：10月24日0:00-10月30日23:59
> 返场价格：1788点券/款
> ```
>
> 页面还带 `发布时间：<time>2026-10-20</time>`，用来给"11月1日"这类缺年份的日期补年份。

> **为什么不用 `herolist.json`？** 它的 `skin_name` 字段更新滞后。实测（2026-11-01）它缺少阿轲  
> 2026-03-06 上线的传说皮肤「罗刹妄海」，而图鉴接口有；且 `skin_name` 只有名字，没有品质、  
> 获取方式、上线时间。所以基线一律以图鉴接口为准。
>
> 也说明：图鉴接口的 `hqfs_8609`（获取方式）记录的是**首次上线**的获取方式，全库没有任何  
> "返场"字样，因此**返场只能靠公告捕捉**——这就是为什么脚本保留两条线。

## 部署（约 5 分钟）

1. 在 GitHub 新建一个仓库（建议 **Public**，Actions 免费且不限时长；Private 每月 2000 分钟也够用）。
2. 把本目录的 `watch.py`、`test_mail.py` 和 `.github/workflows/skin-watch.yml` 按原样（保持 `.github/workflows/` 目录层级）推到仓库的 **main 分支**。
   ```bash
   git init && git add . && git commit -m "init skin watch"
   git branch -M main
   git remote add origin https://github.com/<你的账号>/<仓库名>.git
   git push -u origin main
   ```
3. 配置推送通道（任选其一，两个都配也可以）。

### 方案 A：PushPlus（微信收，最省事，推荐）

1. 打开 <https://www.pushplus.plus>，微信扫码登录，复制你的 **token**。
2. 仓库 → Settings → Secrets and variables → Actions → New repository secret
   - Name: `PUSHPLUS_TOKEN`
   - Secret: 粘贴 token
3. 微信关注 PushPlus 公众号，之后提醒直接推到微信。

### 方案 B：QQ 邮箱（发到你自己邮箱，分步教程）

走完大概 8 分钟。**核心概念只有一句：GitHub 里填的是「授权码」，不是 QQ 登录密码。**

#### 第 1 步：拿到 16 位授权码

1. 电脑浏览器打开 <https://mail.qq.com>，登录你的 QQ 邮箱。
2. 点右上角 **设置** → 选 **账号与安全** 标签（老界面叫「账户」，位置一样）。
3. 往下找 **「POP3/IMAP/SMTP/Exchange/CardDAV/CalDAV服务」** 这一块。
4. 找到 **IMAP/SMTP服务**，点右边的 **开启**。
5. 按提示验证身份：用绑定 QQ 的手机发一条指定内容的短信到指定号码，或直接手机 QQ 扫码。
6. 验证通过后会弹出一串 **16 位字母授权码**，形如 `abcdabcdabcdabcd`。  
   **立刻复制保存**——关掉弹窗就看不到了，忘了只能重新生成（旧码同时失效）。

> 授权码永远不会显示第二次，也支持在「设置 → 账号与安全 → 设备管理 → 授权码管理」里停用或重置。

#### 第 2 步：先在本地验证一下（强烈建议，可跳过）

省得在 GitHub 上反复试错、每次都要看日志才知道哪里错：

```bash
cd wzry-skin-watch
python test_mail.py
```

按提示输入邮箱地址、授权码（输入时不显示）、收件邮箱（直接回车 = 发给自己）。  
看到 `[成功] 已发送！` 就说明授权码没问题，可以进下一步。  
如果报错，脚本会直接告诉你原因（授权码错 / 邮箱写错 / 端口不匹配），照着改就行。

#### 第 3 步：在 GitHub 添加 5 个 Secret

1. 打开你的仓库 → 顶部 **Settings**。
2. 左侧栏 **Secrets and variables** → **Actions**。
3. 点绿色按钮 **New repository secret**，逐个添加下面 5 条（每条都要点一次 New，不能批量）：

| Name（严格照抄，全大写） | Secret 值                   |
| -------------- | -------------------------- |
| `SMTP_HOST`    | `smtp.qq.com`              |
| `SMTP_PORT`    | `465`                      |
| `SMTP_USER`    | 你的 QQ 邮箱，如 `123456@qq.com` |
| `SMTP_PASS`    | 刚才那 16 位授权码（不要带空格）         |
| `MAIL_TO`      | 收提醒的邮箱，填自己就行；多条用英文逗号分隔     |

1. 加完检查一下，列表里应该有 5 条，名字没有拼错、没有多余空格。

> 为什么用 Secret 而不是写在代码里？Secret 是加密存储的，日志里会自动打码，公开仓库也不会泄露。

#### 第 4 步：手动跑一次验证

1. 仓库顶部 **Actions** → 左侧选 `wzry-skin-watch`。
2. 右侧 **Run workflow** → 绿色按钮 **Run workflow**。
3. 等十几秒刷新，点进这次运行，展开 `检查皮肤上新 / 返场` 这一步看日志：
   - 出现 `邮件已发送 -> 你的邮箱` = 成功
   - 出现 `! 邮件发送失败: ...` = 看下面的排查表
4. 去邮箱收信，主题是「王者荣耀皮肤监控已启动」，里面会列出阿轲、司马懿当前的最新皮肤。

#### 收不到 / 发不出？按这个表排查

| 现象                             | 原因                           | 怎么办                        |
| ------------------------------ | ---------------------------- | -------------------------- |
| 日志 `535 Authentication failed` | 授权码错，或 SMTP 服务没开             | 重新生成授权码，确认第 1 步的开关是「已开启」   |
| 日志 `SMTPServerDisconnected`    | 邮箱地址写错（QQ 会直接断连），或端口/加密方式不匹配 | 核对 `SMTP_USER`；465 必须配 SSL |
| 日志 `连接超时`                      | 网络或防火墙拦了 465                 | 把 `SMTP_PORT` 改成 `587` 再试  |
| 发送成功但收不到                       | 进了垃圾邮件箱                      | 在 QQ 邮箱里把发件人加为白名单          |
| 日志里完全没有邮件相关行                   | Secret 名字拼错，脚本读不到            | 对照上表逐字核对 5 个 Name          |

> 自己发给自己时，QQ 邮箱偶尔会把它归到「已发送」或直接不弹通知，建议在邮箱设置里给这个发件人开个提醒。

### 配好后：手动跑一次验证

不管用方案 A 还是方案 B，Secret 配完都执行这一步：

1. 仓库顶部 **Actions** → 左侧选 `wzry-skin-watch`
2. 右侧 **Run workflow** → 绿色按钮 **Run workflow**
3. 等十几秒刷新，点进这次运行，展开 `检查皮肤上新 / 返场` 看日志

日志出现「监控已启动」，同时微信（方案 A）或邮箱（方案 B）收到那条启动消息 —— 说明链路通了。

## 常见问题

- **为什么不是正好 8:00？** GitHub 免费定时任务不保证准点，整点高峰期会排队（实测能晚几小时）。已把触发点提前到北京 07:00，排队后一般 07:10 ~ 08:00 跑完；对皮肤提醒来说早一点晚一点无影响。
- **会不会突然不跑了？** GitHub 对长期无提交的仓库会自动停用定时任务。本脚本每天会更新 `state.json` 并提交，等于自动保活。
- **想换成别的英雄？** 改 `watch.py` 顶部的 `WATCH_HEROES = ["阿轲", "司马懿"]`，英雄名必须和官网一致（如 `李白`、`貂蝉`、`铠`）。
- **想改提醒天数？** 改顶部的 `ALERT_WINDOW_DAYS = 10`，比如改成 `7` 就是 7 天窗口，改成 `1` 就等于只提醒当天。
- **会不会同一款皮肤天天刷屏？** 会每天提醒，但新皮肤**最多 10 天**、返场**到官方结束日为止**，之后自动停。这是刻意的：错过当天还有第二天兜底。
- **会不会漏掉今天的消息？** 不会。新皮肤按上线日期算窗口，返场按官方起止日期算，即使脚本某天没跑成功，第二天只要还在区间内就会补上提醒。
- **返场信息会不会漏？** 主渠道是官方公告正文，能拿到「皮肤 + 起止时间 + 价格」三件套。仍可能漏的是：只在游戏内活动页出现、官网压根没发公告的返场（这种没有任何公开接口可查）。另外公告只写「限定返场皮肤：A、B」不写时间的，会退回 10 天窗口提醒。
- **返场会不会误报？** 已做交叉校验：正文里出现的皮肤名必须同时收录于图鉴该英雄名下才算数，且必须落在「返场时间」上下文里。实测公告里「阿轲-节奏热浪」出现在礼盒随机奖励清单中时，不会被误判成返场。
- **只想本地跑？** `python watch.py` 即可，不依赖第三方库（纯标准库）。但本地跑要求电脑开着。

## 文件说明

- `watch.py` — 抓取、比对、推送全部逻辑，纯标准库，无依赖
- `test_mail.py` — 本地邮件通道自测，先验证授权码再上 GitHub（可选但推荐）
- `.github/workflows/skin-watch.yml` — 云端定时任务定义（UTC `0 23 * * *` = 北京 07:00，预留排队余量）
- `state.json` — 运行后自动生成，记录皮肤基线、已读公告、提醒记录，以及已登记的返场条目（含起止日期）
